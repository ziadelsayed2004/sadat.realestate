# Commission policies

Commission policies are versioned, effective-dated records. Each policy is explicitly `percentage`, `fixed`, or `exempt`, with scope (`default`, provider type, transaction type, property kind, organization, or account) and a stable key. Percentage values use integer basis points; fixed values use integer minor units and an ISO currency. Exempt policies carry neither amount field.

New policies start as `draft`. Activation requires the effective window to contain the current time and rejects overlapping active policies with the same scope. Every mutation requires an expected version and a bounded reason. Lists support strict status/scope/time filters and deterministic ordering. No universal commission value is supplied; later resolver/snapshot tasks select an active policy at a commercial event.

The current implementation is an in-memory service boundary because no persistent commission repository or HTTP composition is present yet. It does not calculate, settle, collect, or claim financial outcomes.

Account overrides use the same explicit percentage/fixed/exempt value rules and effective windows. An account read model reports `source` (`account_override`, `policy`, or `none`), the effective timestamp, and the selected policy version when a default policy applies. Active overrides are mutually exclusive for one account and all writes use optimistic versions and reasons; providers cannot modify or read administrative account override records.

Account commission exceptions are separate, account-scoped records with an explicit `percentage`, `fixed`, or `exempt` value, a bounded effective window, and a required business reason. New exceptions start as `draft`; activation is an administrative approval action that records `approvedBy`, `approvedAt`, and the approval reason. Active exceptions for one account cannot overlap, and an active exception cannot be edited retroactively; it must first be made inactive. The internal `findActiveException` lookup is deterministic and is intended for the later resolver task, where exception precedence over account overrides and default policies is applied.

The exception implementation is an in-memory service boundary because persistent commission repositories and HTTP composition are not present in the current runtime. It does not settle, collect, waive, or claim any financial outcome by itself.

The resolver composes the three explicit sources in product order: active exception, active account override, then active default policy. It returns source identity, source version, effective timestamp, and the selected value; if no source is active it returns an explicit `none` result. Selection is deterministic at temporal boundaries and does not invent a default percentage.

An approved-commercial-event adapter can call `resolveAndSnapshot` with an immutable event identifier, `commercialEventStatus: approved`, account, and approval timestamp. The snapshot stores the resolved source, record identity, version, value, effective timestamp, and capture metadata. Replaying the same event and resolution is idempotent; changing an existing event's resolution is rejected. Because the repository has not defined the approved commercial event or settlement workflow, this boundary performs no financial execution and does not claim that a commission is owed or collected.

Confirmations are account-scoped acknowledgements of a selected policy, account override, or exception. A verified provider may acknowledge only its own account; the server records the acknowledgement timestamp and policy version, and the strict account/version key prevents duplicate or conflicting acknowledgements. A newer acknowledgement supersedes an earlier acknowledged record while preserving its history. Verified administrators may list and inspect confirmations and may revoke one with an optimistic version and reason. Providers can read their own records, but cannot acknowledge another account or mutate/revoke a confirmation. These records express acknowledgement state only and do not authorize settlement or collection.

The commission change-log projection is read-only and accepts only a supplied audit source that returns already-redacted, schema-valid audit records. It allowlists commission policy, exception, account-override, and confirmation targets, preserves before/after snapshots, actor, action, reason, request/trace identifiers, and extracts effective dates from the snapshots. Administrative filters and pagination are strict and deterministic; unrelated audit records are rejected rather than silently presented as commission history. No synthetic change history is created when the audit source is unavailable.

The provider projection is a separate read-only boundary for the planned `GET /api/v1/provider/commission` route. It accepts only a resolver-owned resolution for the authenticated provider subject, maps the internal source version to `policyVersion`, and omits source record IDs, approval actors, reasons, and other administrative fields. Only a verified provider can read it; an owner mismatch is rejected as not found. When no active source exists, the response explicitly uses `source: none` rather than inventing a universal value. The current runtime has no HTTP composition or persistent commission repository, so the provider service exposes an adapter boundary and does not add an unconnected route.
