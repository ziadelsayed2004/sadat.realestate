# Provider advertising projection

The provider advertising projection is an owner-scoped read boundary for the advertising request workflow. A verified provider receives only requests whose persisted `providerId` equals the authenticated subject. Invalid IDs, missing records, and mismatched source ownership fail closed; no administrative or cross-provider lookup is exposed.

Each projection contains the request state and interval, a bounded transition history, an optional quote with integer minor-unit totals and decision history, private payment-proof status/security metadata, and an optional `Africa/Cairo` schedule projection. Storage keys, download URLs, actor identifiers, credentials, and bank-verification claims are deliberately excluded. Payment-proof states remain `pending_review` or `approved` only when the separate review service has recorded that state; the projection does not infer payment or bank verification.

Assisted creation uses `POST /api/v1/provider/ads` with `{ requestMode: "assisted", contactPhone, purpose }`. The verified provider supplies only a contact number and a 2–500 character description. Egyptian local mobile numbers (including Arabic numerals) normalize to international format. Ownership derives from bearer claims. The persisted request immediately enters `review`; it has no invented placement or dates. Administrators assign the active permitted placement and Cairo display period when issuing the quote. The legacy placement/purpose/interval draft payload remains supported. Unknown fields, invalid phone numbers and reversed intervals are rejected. Pending provider applications cannot submit advertising requests.

List results use strict status filters and bounded pagination, then deterministic newest-first ordering. The runtime exposes the owner-scoped `GET /api/v1/provider/ads` and `GET /api/v1/provider/ads/:adRequestId` routes after provider authentication. A verified administrator with `admin:ads.price` issues a manual quote through `POST /api/v1/admin/ad-requests/:adRequestId/quote`; the owning verified provider accepts it through `POST /api/v1/provider/ads/:adRequestId/accept-quote` with an expected quote version. Both mutations use the persistent `ad_requests` and `ad_quotes` collections, optimistic version checks, and transaction boundaries; in-memory fixtures remain test-only. Quote acceptance records provider intent and does not verify a bank payment.
