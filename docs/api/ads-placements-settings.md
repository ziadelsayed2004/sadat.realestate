# Advertising Placements and Settings

Advertising placements use stable logical keys, localized labels, bounded media dimensions, surface scope, locale allowlists, activation, and deterministic ordering. Administrative settings require a verified administrator, strict allowlists, a reason, and optimistic versioning. Placement configuration contains no universal advertising price; payable amounts are created later through the quote workflow.

API startup backfills a missing `homepage.featured` placement for older installations with an administrator-configured `homepage.hero`. The featured card inherits the original setup actor and activation, uses the same defaults as explicit banner setup, and is offered by assisted-request pricing when active. Insert-only initialization preserves existing custom or disabled placements, does not enable global advertising settings, and never publishes a banner. Installations without an original setup actor still use explicit banner configuration.

Featured advertiser options use the provider account ID, with application/profile aliases for existing cards. Eligible accounts can advertise their own published properties without a separate organization page; the approved business name comes from the provider application when no organization name exists. Private owner names are never substituted. Organization and project destinations require a real approved organization page. Featured advertising accepts all approved provider types, including individual brokers, offices without a directory subscription and developers without a commission acknowledgment. Directory identity requirements remain separate. Account, application and profile approval are still required; restricted or deleted accounts cannot advertise. A public display/business name is required and the private account-owner name is never substituted. Account discovery scans past ineligible application batches while keeping the response bounded to 100 distinct eligible accounts.

Advertising settings also hold explicit payment destinations in `vodafone_cash_payment_details`, `instapay_payment_details`, `bank_transfer_payment_details` and `cash_payment_details`: one to ten plain text lines, each at most 200 characters. Administrators enter the beneficiary name and receiving number/account separately from customer contact information. The owner-scoped provider request detail exposes these as `paymentInstructions`; the proof form shows only the selected method's lines, or an explicit request to contact administration if they are absent. No recipient is inferred from contact numbers, no real recipient is seeded, and receipt submission/review remains unchanged.

Quotes are issued only by a verified administrator with `admin:ads.price` for a request waiting for pricing through `POST /api/v1/admin/ad-requests/:adRequestId/quote`. Each quote carries integer minor-unit line items, an ISO-4217 currency code, a future expiry, bounded terms, and append-only decision history. A verified owning provider may accept an issued quote once through `POST /api/v1/provider/ads/:adRequestId/accept-quote`; administrators may reject or cancel it with a reason. Quote acceptance advances the request to `waiting_payment`; this records provider intent only and does not claim bank or payment verification. Quote and request state changes are persisted transactionally with optimistic version checks.

Scheduling is administrator-controlled. A request can become `scheduled` only when its interval has not ended and no other scheduled or active request overlaps the same placement. `active` is allowed only during the stored interval, and `ended` only after it. Calendar projections include both the original instants and deterministic `Africa/Cairo` local start/end values; they do not infer a payment, price, or publication result.

The HTTP scheduling boundary is `POST /api/v1/admin/ad-requests/:adRequestId/schedule` with the strict body `{ "expectedVersion": number }`. It requires a verified administrator with `admin:ads.schedule`, applies optimistic version checks, and rejects expired intervals or placement conflicts. The calendar boundary is `GET /api/v1/admin/ad-calendar`, protected by `admin:ads.view`, with optional placement, status, interval, page, and limit filters. Both responses expose only the bounded calendar projection; they do not expose payment-proof storage keys, internal notes, or administrator-only audit data.

## Banners and public publication

Banner records are strict, versioned administrative data. A banner references one active placement, localized title/alt text, an explicit HTTPS target when the placement requires it, a deterministic sort order, and an explicit public media record. Media metadata accepts HTTPS image URLs or safe same-origin root-relative image paths, including legacy CMS assets and authenticated banner-media URLs, with declared dimensions. Protocol-relative, escaped and traversal paths are rejected. Metadata never contains private storage keys or credentials. Media cannot be deleted while referenced by a banner.

Banner status transitions are guarded (`draft` → `scheduled` → `active` → `ended` → `archived`, with archival allowed from non-terminal states). Scheduling validates the interval and placement. Activation additionally requires an active placement, enabled advertising settings, a linked media record, the target URL requirement, the active time window, capacity, and no overlapping scheduled/active banner in the same placement. Every mutation uses an expected version and a reason.

Administrative preview and list operations may return draft or inactive records. Public projections are separate: they include only `active` banners whose interval contains the request time, whose placement and advertising settings are active for the requested surface, whose locale is allowed, and whose media is active. Public ordering is placement order, banner sort order, then stable ID. Localized title and alt text are resolved with deterministic `ar` → `en` → `zh-CN` fallback while the keyed localized objects remain available.

The administrator banner boundary is exposed through `GET`/`POST /api/v1/admin/banners`, `PATCH /api/v1/admin/banners/:bannerId`, `GET /api/v1/admin/banners/:bannerId/preview`, `GET`/`POST /api/v1/admin/banners/:bannerId/media`, `PATCH`/`DELETE /api/v1/admin/banner-media/:mediaId`, and `POST /api/v1/admin/banners/order`. Reads require `admin:banners.view`; mutations require `admin:banners.manage`. Mutation bodies are strict, reason-bearing, and version-checked. The production runtime stores banner and media records in MongoDB and returns only the contract projection; deterministic in-memory service tests remain available for local verification.

Uploaded image downloads use `GET /api/v1/public/banner-media/:mediaId`. Anonymous downloads still require public publication. When an administrator bearer token is supplied, the administrative authentication and session policy applies before private draft-image access: invalid or expired credentials return 401, while a wrong role or insufficient permission returns 403. The administrative image loader refreshes a failed authenticated session once and retries with the new token. Non-image responses are rejected. The featured editor offers a separate preview retry without clearing form edits or saving content, and releases preview object URLs when closed or replaced.

The featured table opens editing and a separate saved-content preview, scrolling/focusing the selected panel. Preview is read-only and supports unlinked imported drafts without fabricated advertiser identity. Current public homepage projection verifies site links; only a publicly visible card offers its link, selecting that exact card via `featuredAd` in the homepage carousel. Hidden/draft rows explain why the site action is unavailable, and Refresh rechecks both list and visibility. Row arrows preserve unique existing positions or assign unique positions to tied legacy rows, submitting optimistic versions and reporting completion.
