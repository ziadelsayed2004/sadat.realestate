# Projects and provider-owned CRUD

Projects use stable IDs and logical slugs, localized names/descriptions for `ar`, `en`, and `zh-CN`, optional approved location and organization references, and the project lifecycle defined by the product state machine. Provider CRUD is restricted to verified provider bearer sessions and filters every read/update by the authenticated provider ID; ownership, provider IDs, verification flags, and review fields are never accepted from client payloads. Authorized verified administrators with `admin:projects.view` can list all projects through the separate admin projection used for review screens.

Create starts a `draft`. Updates require the current optimistic version and preserve the draft boundary. A verified provider submits a draft or `needs_changes` project with a reason and version, moving it to `pending_review`. An authorized Admin with `admin:projects.review` may move `pending_review` to `needs_changes`, `approved`, or `rejected`, then publish an approved project. Each transition records the actor, reason, request, trace, reviewer, and timestamps through the existing audit writer; stale versions and invalid state transitions fail closed. Public projection and revisions remain owned by later B3 tasks.

No production projects or map coordinates are seeded. Location and organization references are optional and can remain empty until approved master data is available.

`GET /api/v1/admin/projects` accepts the same strict status, search, sort, direction, page, and limit query as the provider list. It returns the paginated `ProjectListData` envelope with review fields and server-derived `availableActions`; the route never accepts an owner/provider filter from the client. The shared admin middleware requires a verified admin session and the project service requires `admin:projects.view`.

Public project details open at `/developers/:developerSlug/projects/:projectSlug?lang=ar|en`. The page uses the existing `GET /api/v1/public/developers/:slug` projection and selects a published project within that approved developer's profile. It shows saved project media, description, location, unit/area/price/delivery labels when present, and only published active properties whose `projectId` matches the selected project. Inquiries preselect that project. Missing or unpublished projects return a 404 page with noindex metadata; no other project is substituted. Legacy developer-card anchors still locate the card, whose “View project” link opens the independent page.

Admin `ProjectData.publicPath` and featured advertisement project destinations point to the independent page. The admin link remains absent for unpublished projects or developers without an approved organization/profile. These are web navigation paths, not additional API routes. Original records and linked properties remain intact when a project is archived.
