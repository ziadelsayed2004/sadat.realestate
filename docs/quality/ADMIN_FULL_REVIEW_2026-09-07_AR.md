## خلل قائمة العقارات وإصلاحه

كان `/api/v1/admin/properties?sort=updatedAt&direction=desc&page=1&limit=20` يرجع `400 VALIDATION_FAILED` بسبب سجل قديم في Production يحتوي `paymentPlans` بصيغة تسبق العقد الحالي. الحقول الجديدة المطلوبة هي `name`, `installments`, `frequency`, `installmentAmount`.

تم إصلاح طبقة العرض في خدمة العقارات لتتجاهل فقط خطط السداد القديمة غير القابلة للعرض بدل إسقاط قائمة العقارات كاملة، مع الحفاظ على كل الخطط الحديثة الصحيحة. هذا حل backward-compatible وآمن للقراءة؛ ويمكن تنفيذ migration منفصلة لاحقًا إذا توفرت قواعد تحويل مؤكدة للقيم القديمة.

التحقق:

## فلو مقدم العقار والمراجعة

الفلو المطبق حاليًا يفصل بين ثلاثة مستويات:

1. إنشاء الحساب وإكمال طلب التوثيق مسموحان قبل الموافقة.
2. إنشاء أو رفع عقار/مشروع محمي في الـAPI ويتطلب مقدم عقار بحالة `verified`.
3. المحتوى يبدأ `draft`، ثم `pending_review` عند الإرسال، ولا يظهر للعامة إلا بعد اعتماد Admin والوصول إلى `published`.

أضيف قيد باك إجباري للمشروعات: حساب مقدم العقار يجب أن تكون معاملته معتمدة ونوعه `developer_company`. لذلك لا يستطيع البائع الفردي أو مكتب الوساطة تجاوز الواجهة وإنشاء مشروع باستدعاء الـAPI مباشرة؛ بينما تظل العقارات متاحة للأنواع الثلاثة بعد اعتماد الحساب.

صفحة تفاصيل مقدم العقار تستهلك `availableActions` من الخادم وتدعم: الاعتماد، طلب استكمال بيانات، الرفض، والإيقاف، مع سبب إلزامي. وبعد اعتماد الحساب يتم تحديث جلسة مقدم العقار لمنع بقاء صلاحية `pending` القديمة في access token.

## مقارنة Figma الصادقة

ربط المسارات ومراجع الصور يشمل الشاشات الـ64 ذات المصدر المؤكد. تعذر جلب سياق Figma حديث خلال هذه الجولة بسبب طلب إعادة توثيق الموصل، لذلك استُخدمت تصديرات `docs/design_sources/final_screens/admin/` المثبتة في المستودع بوصفها المرجع القابل لإعادة الاختبار. `ADM-01` أُعيد تنظيمها لتطابق بنية المرجع الأقرب، مع عزل قواعدها المكتبية حتى لا تغيّر تخطيط بقية شاشات الإدارة.

نجاح snapshots يثبت ثبات التنفيذ الحالي بعد الإصلاح، لكنه لا يحول اختلاف البيانات أو الأبعاد عن تصدير Figma إلى تطابق بكسلي 100%. لذلك تظل نسب المقارنة المباشرة القديمة أدناه مؤشرات صادقة لا نسب إنجاز مصطنعة.

المقاييس البكسلية الموجودة في المستودع (للاسترشاد فقط بسبب اختلاف كثافة البيانات وأبعاد المستند):

| الشاشة | الفرق المادي المسجل | التطابق الحسابي التقريبي |
|---|---:|---:|
| `ADM-01` | 51.7288% | 48.2712% |
| `ADM-04` | 41.3434% | 58.6566% |
| `ADM-66` | 51.6080% | 48.3920% |

هذه الأرقام تمنع ادعاء 100% حاليًا. الإغلاق الحقيقي يحتاج إعادة التقاط runtime بعد نشر الإصلاحات، ثم مقارنة كل frame بحالة بيانات مماثلة، لا الاكتفاء بنجاح الاختبارات الهيكلية.
